# 按来源感知的目标选择（access-aware target picking）

## 背景与改动

此前 `allow=ip:` / `deny=ip:` 只在选定目标之后由 `Target.AccessDeniedHTTP` 判定：
`proxy/http_proxy.go` 先 `Lookup` 按权重选出目标，被拒绝就直接 403，不会改选其他目标。
两条路由 `a(allow=ip:10.0.0.0/8)`、`b(allow=ip:192.168.0.0/16)` 并存时，来自 10.1.2.3
的请求约一半拿到 403。

本次改动把过滤提前到选择阶段：对含有访问规则的路由，先排除不允许当前请求来源的目标，
再在剩余目标里按权重选择。改动点：

- `route/route.go`
  - `Route` 新增 `hasAccessRules` 标志，由 `weighTargets` 维护。`weighTargets` 在
    `addTarget`、`filter`（route del）、`setWeight`（route weight）之后都会执行，
    因此该标志不会过期；候选子集不做预计算、不做缓存，每个请求现算，被删掉的目标
    不可能再被选中。
  - 新增 `Route.pickTarget(req, pick)`：无规则路由、单目标路由、`req == nil`
    （`LookupHost`）走原有路径，零额外分配；有规则路由先逐目标（不是逐槽位）做一次
    判定，再在过滤后的环视图上调用原 picker。
  - `total` 由 `uint64` 改为 `*uint64`，使过滤视图与路由共享同一个 rr 计数器。
- `route/table.go`：私有方法 `lookup` 增加 `req` 参数并转交 `pickTarget`；
  `Lookup` 传入请求，`LookupHost` 传 `nil`。`Lookup` 与 `picker` 的签名不变。
- `route/picker.go`：`rrPicker` 改为单次 `atomic.AddUint64` 取号，消除原先
  「读 `r.total` 再原子加」之间的数据竞争（-race 在并发选取场景下会报告）。
- `route/access_rules.go`：判定与日志分离（见下）。

全部被排除时不返回 nil：`Lookup` 在 `lookup` 返回 nil 后会继续尝试其他主机模式和
无主机的通用路由，若用 nil 表达「全部排除」，本应 403 的请求会被送进 catch-all 路由。
因此全部排除时回退为按原权重选出的目标（必然是被拒绝的目标），调用方
`AccessDeniedHTTP` 照常给出 403，调用方代码无需任何改动。

## 剩余目标的比例：选择算法甲

两种候选算法：

- **算法甲（选定）**：在原有加权环上只保留允许目标的槽位，剩余目标之间的比例等于
  它们在原环上的槽位数之比。
- **算法乙（放弃）**：对剩余目标重新执行一次 `weighTargets` 的规则（固定权重归一化、
  动态权重平分剩余）。

选甲的理由：

1. **乙会把流量发给原表里份额为零的目标。** 输入：a、b 固定权重各 0.5，c 动态权重，
   a 带 `deny=ip:10.0.0.0/8`。原环上 a、b 各占 5000 槽，c 占 0 槽（固定权重之和已为
   1，动态权重为 0）。来自 10.1.2.3 时 a 被排除：按乙，对 {b(0.5 固定), c(动态)}
   重新加权得 b、c 各 0.5——c 拿到了它在原表里从来没有的一半流量，运营者显式配置的
   「c 不分流」被静默推翻。按甲，c 仍是 0 槽，全部流量到 b。
2. **甲不会发明新的比例。** 子集比例永远是已配置比例的粗化（删掉若干槽位），任何
   幸存目标的相对份额都可以直接从原配置推出；乙在每次过滤后重新解释权重，同一组
   目标在不同来源下比例含义不同。
3. **甲更便宜。** 过滤现有环是 O(槽数) 的一次遍历；乙需要按来源重新执行加权算法，
   要么每请求重算，要么按来源缓存并在每个 `weighTargets` 调用点后重建缓存。

**甲与直觉不符的输入**：a 固定权重 0.2，b、c 动态，c 带 `deny=ip:10.0.0.0/8`。原环
a 占 2000 槽、b、c 各占 4000 槽。来自 10.1.2.3 的请求按甲在 a、b 间是 2000:4000，
即 a 占 1/3、b 占 2/3——而不是「a 拿 0.2、b 拿 0.8」（那是算法乙的结果）。也就是
说固定权重在过滤后不被保持为绝对份额，只保持幸存者之间的相对槽位比。这一行为是
有意的：见上，乙的「保持固定权重」恰恰是把零份额目标重新引入流量分配的机制。

## rr 在候选子集上的计数

子集视图与路由共享同一个原子计数器（`Route.total`），选取时下标为
`counter % 子集槽数`。因此：

- 同一子集上**连续**调用「子集槽位总数」次，计数器恰好遍历一遍全部余数，每个槽位
  被命中恰好一次——各目标命中次数与算法甲的槽位比例**完全一致**（测试
  `TestAccessAwarePickSlotRatios` 用 6000 次调用验证 2000:4000）。
- 不同子集（不同来源）交错、或子集随路由变化时，不保持严格轮转：计数器是全局递增
  的，交错会跳过某些槽位。这是有意的取舍，换来无锁、无缓存、无状态泄露的实现。
- 计数器的所有访问都是原子的，`-race` 干净（测试
  `TestAccessAwarePickConcurrency`：两组 goroutine 用起跑栅栏同时开始，各发 6000
  个请求，10.1.2.3 组全部落 a、192.168.1.1 组全部落 b，与交错先后无关）。

rnd 策略在子集上等概率取槽位，比例同样收敛到槽位比。

## 判定与日志分离

`route/access_rules.go` 现在只有一份判定逻辑：

- `checkIPRules(ip)`：IP 对规则的判定，不输出日志。`denyByIP`（供
  `AccessDeniedTCP` 使用）= `checkIPRules` + 一条 INFO 拒绝日志。
- `checkAccessHTTP(req)`：请求级判定，不输出日志，返回 (是否拒绝, 触发拒绝的 IP)。
  语义与 `AccessDeniedHTTP` 完全一致：RemoteAddr 与 X-Forwarded-For 的每个元素都
  要通过、与 RemoteAddr 主机相同的元素跳过、无法解析的元素跳过、RemoteAddr 无法
  解析（含 gRPC 没有 RemoteAddr）时按允许处理。
- `AccessDeniedHTTP` = `checkAccessHTTP` + 日志。过滤阶段（`pickTarget`）只调用
  `checkAccessHTTP`，不为被排除的目标记日志。

结果：被正常转发的请求不产生拒绝日志；以 403 结束的请求恰好一条
`route rules denied access`，与现状相同（测试 `TestAccessAwarePickDenialLogCounts`）。

两处有意的日志差异（不影响判定，仅诊断输出）：

- `denyByIP` 原有的 DEBUG 级逐条匹配日志被移除（判定已下沉到 `checkIPRules`，
  保留意味着过滤阶段每请求刷 DEBUG 日志）。
- RemoteAddr/XFF 无法解析时的 ERROR/WARN 诊断仍在 `AccessDeniedHTTP` 中保留，但
  当请求最终被拒绝时，这些 WARN 不再先于 INFO 出现（判定先返回，诊断后补）。

## 边界行为

- **gRPC**：`proxy/grpc_handler.go` 构造的请求没有 RemoteAddr，按「无法解析即允许」
  处理，所有目标都通过过滤，选择结果与改动前完全一致（测试
  `TestGRPCAccessRulesIgnored`：两个目标都带规则，rr 仍在二者间轮转）。gRPC 依旧
  不执行 `AccessDeniedHTTP`，本改动不引入 gRPC 侧的 403。
- **TCP**：`AccessDeniedTCP` 在连接建立后判定，没有请求对象，不在本次范围内，行为
  不变（`LookupHost` 传 nil 请求，不过滤）。
- **无规则路由**：走原有路径，`testing.AllocsPerRun` 断言 `Lookup` 分配次数不超过
  改动前基线 2 次（测试 `TestLookupAllocsNoRules`）。

## 无法解析的规则：兼容性说明（维持现状，待确认）

`route.go` 的 `addTarget` 对 `ProcessAccessRules` 返回的错误只记 ERROR 并保留目标
上线。三种情形当前表现如下，本次**均未改变**：

1. `deny=ip:bad`：规则整体解析失败，`accessRules` 为空，目标对**所有来源**开放。
2. `allow=ip:10.0.0.0/8,ip:bad`：前半部分保留——`accessRules` 里只有 10.0.0.0/8
   这一条 allow，目标按部分规则生效（注意：这意味着除 10/8 外的来源都被拒，比
   「规则不存在」更严格，配置者看到的可能只是日志里一条 ERROR）。
3. `allow` 与 `deny` 同时写：`ProcessAccessRules` 直接返回错误，一条规则也不生效，
   目标对**所有来源**开放。

倾向的后续方向是「规则非法则该目标不上线，并记录目标与原始规则文本」，但它会改变
现有配置的表现：情形 1、3 的目标会从「对所有人开放」变为「根本收不到流量」，情形 2
会从「部分生效」变为「不生效」。对把非法配置当放通用的部署是破坏性变更，因此本次
维持现状，是否切换待确认。注意无论选择哪种，过滤阶段的判定都与 `AccessDeniedHTTP`
一致，两种选择下「先过滤再选择」的语义都成立。

## 对照表

表 A：`route add svc foo.com/ http://a:1/ opts "allow=ip:10.0.0.0/8"` 与
`route add svc foo.com/ http://b:2/ opts "allow=ip:192.168.0.0/16"`（动态权重）。

| 请求来源 | 改动前分布 | 改动前状态码/拒绝日志 | 改动后分布 | 改动后状态码/拒绝日志 |
|---|---|---|---|---|
| 10.1.2.3 | a、b 各约一半 | 到 a 200；到 b 403，每次 403 一条 INFO | 全部 a | 全部 200，0 条 |
| 192.168.1.1 | a、b 各约一半 | 到 a 403（一条 INFO）；到 b 200 | 全部 b | 全部 200，0 条 |
| 172.16.0.1 | a、b 各约一半 | 全部 403，每条请求一条 INFO | 全部排除，回退原权重选出 a 或 b | 全部 403，恰好一条 INFO |
| 10.1.2.3，XFF `10.1.2.3, 172.16.0.9` | a、b 各约一半 | 全部 403（XFF 元素 172.16.0.9 两者都不允许），一条 INFO | 全部排除，回退原权重 | 全部 403，恰好一条 INFO |
| `[::ffff:10.1.2.3]:5000` | a、b 各约一半 | 到 a 200；到 b 403（一条 INFO） | 全部 a | 全部 200，0 条 |
| 同上表加无规则目标 d：`[2001:db8::1]:443` | a、b、d 各约 1/3 | 到 a、b 403（一条 INFO）；到 d 200 | 全部 d | 全部 200，0 条 |
| RemoteAddr 无端口（SplitHostPort 失败） | 按允许处理 | 分布与无规则相同，无拒绝日志 | 按允许处理（同前） | 分布与无规则相同，无拒绝日志 |

| 172.16.0.1 访问 bar.com | 落到无主机路由 → 200 | 不变 → 200 |

表 C：a（allow 10/8）与 d（无规则）两个动态目标，rr。
